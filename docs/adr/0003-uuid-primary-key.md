# 0003. 기본키를 UUID로 한다

## 상태

채택 (2026-09-18)

## 맥락

모든 엔티티는 식별자를 하나씩 갖는다. 그 값을 데이터베이스가 순차로 발급할지, 애플리케이션이 임의 값으로 만들지 정해야 한다.

이 선택은 나중에 바꾸기 어렵다. 기본키 타입은 그 엔티티를 참조하는 **모든 외래키로 전파되고**, 식별자가 API 경로에 실리는 순간 외부와 맺은 계약의 일부가 된다. 엔티티를 하나 추가할 때마다 같은 선택이 반복되므로, 첫 엔티티를 쓰기 전에 한 번 정해 두어야 한다.

## 검토한 선택지

### (1) Long + IDENTITY

데이터베이스가 순차 정수를 발급한다.

**이 선택지가 주는 이점은 여러 겹이다.** 순차 정수는 인덱스에 순서대로 삽입되므로 B-tree 페이지 분할이 거의 일어나지 않는다. 8바이트로 UUID의 절반이고, 이 차이는 기본키 컬럼 하나에 그치지 않고 **모든 외래키와 그 인덱스에 곱해진다.** 그리고 사람이 읽고 말할 수 있다 — 로그에서 대출 번호를 눈으로 좇거나, 문의 대응 중에 번호를 불러주는 일이 가능하다.

단일 데이터베이스에서 순차 발급이 병목이 되지 않는 규모라면 **이쪽이 더 나은 선택이다.**

한계는 **값 자체가 정보를 흘린다**는 데 있다. 순번은 그 자리에 있는 것만으로 전체 개수를 알려준다.

### (2) UUID

애플리케이션이 임의의 128비트 값을 만든다.

한계는 순차성이 주던 것들을 모두 잃는다는 데 있다 — 삽입 위치의 국소성, 절반의 크기, 사람이 읽을 수 있음, 그리고 생성 순서.

## 결정

**모든 엔티티의 기본키를 UUID로 한다.** 식별자는 애플리케이션에서 생성하며, 데이터베이스가 발급하지 않는다.

## 근거

**첫째, 순차 식별자는 값 자체로 규모를 노출한다.** URL이나 응답에 실린 순번은 총 회원 수나 누적 대출 건수를 추측하게 한다. 이 시스템은 대출과 복본의 식별자를 경로에 그대로 담으므로, 식별자를 받아 본 사람은 누구나 그 추측을 할 수 있다. UUID는 값에서 아무것도 유도되지 않는다.

**둘째, 애플리케이션에서 미리 생성할 수 있다.** 데이터베이스 왕복 없이 식별자를 정할 수 있으므로, 서로를 참조하는 객체들을 메모리에서 한 번에 조립한 뒤 저장할 수 있다. 순차 발급은 "저장해 봐야 번호를 안다"는 순서 제약을 만든다.

**셋째, 병합과 이관에서 충돌이 없다.** 지점별로 나뉜 데이터를 합치거나 환경 간에 옮길 때 키를 다시 매길 필요가 없다. 순차 정수는 두 집합을 합치는 순간 반드시 겹친다.

### 데이터베이스 타입 매핑은 Hibernate에 맡긴다

엔티티에 `columnDefinition`을 명시하지 않는다. PostgreSQL은 `uuid` 타입을 네이티브로 지원하므로 Hibernate가 알아서 매핑하고, MySQL이라면 다른 표현을 고른다. `BINARY(16)` 같은 벤더 종속 정의를 엔티티에 박아 넣으면 그 순간 이식성이 사라진다 — 엔티티는 "이것은 UUID다"까지만 말하고, 어떻게 저장할지는 방언이 정하게 둔다.

## 포기한 것

- **인덱스 삽입 성능.** 랜덤 UUID는 B-tree의 무작위 위치로 들어가므로 페이지 분할이 잦다. 행이 계속 누적되는 대출 테이블에서 가장 먼저 체감될 지점이다.
- **저장 공간.** 8바이트 대비 16바이트이며, 이 차이가 모든 외래키 컬럼과 인덱스에 반복된다. 대출은 이용자와 복본 두 방향을 참조하므로 한 행에서만 세 번 곱해진다.
- **가독성.** 로그에서 특정 대출을 좇거나 문의에 대응할 때 사람이 읽고 받아적기 어렵다. 순차 정수가 공짜로 주던 편의다.
- **정렬.** 순차 식별자는 생성 순서를 값 안에 담지만 UUID는 담지 않는다. 생성 순 정렬은 별도의 생성 시각 컬럼에 의존해야 한다.

## 재검토 조건

**되돌리는 방향 — 측정된 병목이 있을 때만.** 기본키 타입을 바꾸면 여섯 엔티티의 기본키와 일곱 개의 외래키 컬럼을 전부 다시 매겨야 한다. "느릴 것 같다"로 착수할 수 있는 작업이 아니다. 삽입 지연이나 인덱스 크기가 **실제로 측정된 뒤에만** 이 문서를 다시 연다.

**강화하는 방향 — UUIDv7.** 삽입 성능이나 정렬이 실제 문제가 되면, 되돌리기 전에 **시간 정렬이 가능한 UUIDv7로 바꾸는 길**이 있다. 포기한 것 네 가지 중 인덱스 삽입과 정렬 두 가지를 **기본키 타입을 유지한 채** 해소한다. 외래키도 API 계약도 그대로다. 두 방향의 비용이 이렇게 비대칭이므로, 문제가 생기면 먼저 볼 곳은 이쪽이다.

**비가역 지점.** 외부 시스템이나 클라이언트가 이 식별자를 자기 쪽에 저장하기 시작하면 변경이 닫힌다. 그 시점부터는 우리 데이터베이스만 고쳐서 끝나지 않는다.
